## 1. 核心目标（唯一判定标准）

系统对一批真实评论，必须输出五个正确的结果：

| 输出 | 系统里对应什么 |
|---|---|
| 产品问题 | TOP10 问题标签 + 原文证据 |
| 产品亮点 | TOP10 亮点标签 + 原文证据 |
| 消费者画像 | 谁在用 / 怎么用 / 什么场景 |
| 购买动机 | 为什么买 |
| 未满足需求 | 想解决但没解决的 |

两条底线：

- **不错标** — 标签说的话，原文里真的有。
- **不漏标** — 原文说了的重要内容，没被丢掉。

**达不到这五个输出 + 两条底线，系统不交付给真实用户。** 这条优先于任何其它功能排期。

## 2. 片段流向表（模块分流唯一口径）

正式 `module` 只有六个：`product_issue`、`product_highlight`、`consumer_profile`、`purchase_motive`、`unmet_need`、`audit_filter`。

| 评论片段说的内容 | 应该流向 |
|---|---|
| 产品哪里好 | `product_highlight` |
| 产品哪里不好 | `product_issue` |
| 谁在用 | `consumer_profile`（人群特征） |
| 用户怎么用 | `consumer_profile`（用户行为） |
| 在哪里、什么时候、什么场景用 | `consumer_profile`（使用场景） |
| 为什么买 | `purchase_motive` |
| 想解决但没解决的事 | `unmet_need` |
| 配件、包装、发货、尺码表、详情页等卖家可行动负面反馈 | `product_issue` |
| 客服服务好 / 差 | `product_highlight` / `product_issue` |
| 旧产品、竞品、替代品 | `audit_filter` |
| 无法划分、无证据、无行动价值 | `audit_filter`（不进正式 TOP10） |

`customer_service` 不是独立 module。正向进 `product_highlight`，负向进 `product_issue`。

## 3. 标签身份三层（不可互相替代）

| 层 | 是什么 | 谁定义 |
|---|---|---|
| `module` | 这段话属于哪个业务模块 | 上面第 2 节的流向表 |
| `aspect_key` | taxonomy 证据维度（如 `seam_integrity`、`waterproof`） | `category_aspect_taxonomy`，按 `sub_category` 白名单 |
| `issue_key` / `highlight_key` | 卖家可读的正式 TOP10 聚合身份（如 `water_leaks_through`） | 统一 registry + resolver |

正式 TOP10 行必须有 `issue_key` 或 `highlight_key`，不能只靠 `aspect_key`。`action_label_key` 和 formal `normalized_label` 已删除，不得复活。

正式标签能展示，必须**同时**满足五条：当前评论有原文证据、当前产品 scope 已知、当前 taxonomy 支持该语义、registry 状态为 `approved`、resolver 在当前 category/sub_category 下通过。

## 3.1 一条评论到最终结果的目标链路

1. 用户上传评论。
2. 系统清洗：去空、去重、识别评分 / SKU / 产品。
3. 系统识别产品 `sub_category`。
4. 读取该子品类的 `category_aspect_taxonomy` 白名单 + 模块级 seed taxonomy。
5. **LLM 把评论拆成片段。**
6. 每个片段判断进入哪个模块（六个之一，见第 2 节流向表）。
7. 属于产品问题/亮点：先选当前子品类允许的 `aspect_key` 作为证据维度，再映射到 approved `issue_key` / `highlight_key` 作为 TOP10 聚合身份。
8. 属于消费者画像/使用场景/购买动机：只能从对应模块 seed taxonomy 里选；选不上进 candidate。
9. 属于未满足需求：candidate-first 收集真实表达，不硬贴产品 taxonomy。
10. 没有合适证据维度或 approved 标签 → `audit_filter` / candidate，不进正式 TOP10。
11. 检查标签是否有原文证据、是否属于当前产品、是否越界。
12. 通过门禁的高置信正式标签进入 TOP10 / 报告 / 导出；行动中心用正式 `issue_key` + 证据 + 趋势生成 `suggested_action` 文本。

**行动中心口径**：它不是标签注册中心的下游动作标签库。接收 `issue_key` / `canonical_issue_key`、展示文本、代表性评论、占比和趋势，由 AI 生成 `suggested_action`、标题、优先级。`recommended_action_key` 不作为必需字段。

**registry / taxonomy 分工**：`category_aspect_taxonomy` 负责 `aspect_key` 白名单和证据维度，不直接充当卖家正式问题或亮点。统一 Catalog/resolver 负责正式 `issue_key`、`highlight_key`、alias、适用品类、`boundary_note`、`approved` 状态、中英展示文本、`registry_version`。物流类上层证据维度统一 `aspect_key=logistics_issue`，由 `issue_key=late_shipping` / `shipping_damage` 区分。

## 4. 核心分工原则：AI 负责理解，规则只负责刹车

这是 2026-08-10 讨论确认的架构底线，回答"新类目要不要写规则"。

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| AI（LLM） | 读原文、拆片段、理解语义、判断正负向、指出证据是哪句话 | — |
| 规则 | **只能否决** AI 或其它规则想贴的标签 | **不能自己创造标签** |

**规则不产出标签，只挡掉可疑的。** 样板是 5.9.7-T4（极性对撞守卫）：拿 LLM 已判定的 aspect polarity 去否决规则想贴的标签，零 token 增量成本，覆盖所有品类，历史 session 打开时自动纠正。

### 4.1 三类"规则"必须分开看

| 类 | 性质 | 命运 |
|---|---|---|
| **第 1 类：语义陷阱守卫** — 否定句、正向反例、后段推翻前段、用户自己买错码、好评差评串台、极性对撞 | 通用。任何类目任何语言都有 | **提取为全类目共享**，做一次全类目受益 |
| **第 2 类：类目能力维度** — 某标签只对声明了该能力的类目生效（`scope_policy: capability_derived`） | 配置，不是代码 | 新类目**填表**声明能力维度，系统自动推导适用标签 |
| **第 3 类：硬编码类目关键词** — `wader hanger`、`pocket not waterproof`、`traction`、`flimsy` | 不可复用，只对下水服成立 | **停止新增 + 分批退役**（必须先有基准集数字才敢删） |

### 4.2 5.9.8 为什么失败，5.9.9 淘汰了什么

- 5.9.8 失败的原因不是"用了规则"，是**用规则代替理解**。关键词读不懂否定和转折，补一个 `aren't waterproof`，下一条就来 `wanted these to fit **but**...`，永远补不完。
- 5.9.9 淘汰的是**"围绕单个类目手写规则来证明准确率"这条路线**，不是"系统里不能有任何规则"。
- 判定标准：一条规则如果只对一个类目成立，它是债；如果对所有类目成立且只做否决，它是资产。

### 4.3 新类目上线目标形态（Erika ≈ 35 分钟，不写规则）

| 步 | 谁 | 做什么 | 时间 |
|---|---|---|---|
| 1 | Claude Code | 类目配置里声明该类目的能力维度 | 10 分钟 |
| 2 | 系统 | 自动算出哪些已有正式标签适用 | 自动 |
| 3 | Erika | 上传 50 条真实评论 | 5 分钟 |
| 4 | 系统 | 把没见过的新说法排成候选池 Top 10 | 自动 |
| 5 | **Erika** | 校准页点"晋升 / 合并 / 忽略" | **30 分钟** |
| 6 | 系统 | 跑六指标，过线则开放该类目 | 自动 |

前提：AI 语义理解够准（阶段 C）+ 候选池真的接上生产（阶段 E）。

## 5. 九层质量（每层坏了会看到什么）

| # | 层级 | 管什么 | 2026-08-10 状态 | 坏了会看到 |
|---|---|---|---|---|
| 1 | 评论进来 | 抓取/上传/解析 | ✅ 可用 | 评论缺失、乱码 |
| 2 | 缓存不骗人 | 改了规则后旧结果自动失效 | ✅ 5.9.6-B.1 已修 | 改了没生效，或验的是旧结果 |
| 3 | **拆片段** | 一条评论说了 3 件事要拆 3 段 | ❌ **代码写了，生产没接** | 一条评论只被理解成一件事 |
| 4 | **分模块** | 每段进哪个模块 | ⚠️ 只对问题/亮点生效 | 画像动机需求靠猜 |
| 5 | 标签白名单 | AI 只能从批准过的标签里选 | ⚠️ 问题/亮点有；画像/动机/需求没有 | 同一个意思五种说法，统计不到一起 |
| 6 | 原文证据门禁 | 每个标签能指出原文哪句话 | ⚠️ 有，8-07 / 8-10 各被绕过修了一次 | 无中生有 |
| 7 | 类目范围门禁 | "防水"不能出现在保温杯上 | ⚠️ 机制做完，**线上默认关闭**，只登记 9 个标签 | 标签串类目 |
| 8 | 聚合成 TOP10 | 排序、去重、算占比 | ✅ 可用 | 占比不对、重复标签 |
| 9 | **漏标度量** | 原文说了但没标出来的比例 | ❌ **完全没有度量** | 永远不知道漏了多少 |

第 3、9 层和第 4 层的一半，是当前挡在核心目标前的三项。第 9 层最关键：现有评测只测"情绪判对没有"，不测标签层面错标率，完全不测漏标率——**没有漏标度量，"漏标"这个验收项无法判定**。

## 6. 六个硬指标 + 通过线

| 指标 | 白话解释 | 通过线 |
|---|---|---|
| 错标率 | 标了但原文没说 | ≤ 5% |
| 漏标率 | 原文说了但没标 | ≤ 20% |
| 极性反标数 | 差评被标成亮点，或反过来 | **必须 = 0** |
| 串台数 | 旧款/竞品/物流被算成当前产品 | **必须 = 0** |
| 模块流向正确率 | "为什么买"没跑到"产品亮点"里 | ≥ 90% |
| other 占比 | 系统看不懂的比例 | ≤ 15% |

- 两个 `= 0` 是红线：这两类错误会让卖家做出错误决策，比错标更贵。
- 漏标先设 20%：AI 抽取天然会漏次要表达，一上来卡太紧会逼系统乱标凑数。跑起来后再收紧。

## 7. 基准集

- 3 个类目 × 50 条真实评论。waders（已有，见 `docs/5.9.9-step4.6-waders-351-400-human-gold-assimilation.md`，Erika 2026-08-10 确认桌面标注即该批）+ 服饰 + 3C（Erika 后补，不阻塞）。
- 标注内容：这条评论里哪几句话说了事 / 每句话该进哪个模块 / 该贴什么标签。
- **标完冻结。** Erika 只标一次，之后机器自动对比。每类目 2-3 小时。
  - **冻结规则**：任何 gold 改动必须同步 `expected_*_keys` / `annotated_review_labels[].module_routing` / `module_routing_summary` 三字段，并重跑基线更新文档，否则不算冻结。三字段以 `expected_issue_keys` + `expected_highlight_keys` 为单一事实源，`module_routing` 和 `module_routing_summary` 由它推导。
- 允许先用 waders 单类目跑通脚本拿第一个基线，另两个类目后补。

## 8. 三道闸门（每次标签相关改动都过）

| 闸门 | 谁 | 做什么 | 不过怎样 |
|---|---|---|---|
| 1 | 机器（每次 push） | 跑基准集，输出六指标**改动前 vs 改动后**对比表，接进 CI | 任何红线破 → 拒绝合并 |
| 2 | Erika（15 分钟） | 机器从本次改动影响到的评论里随机抽 10 条，出「原文片段 / 进了哪个模块 / 贴了什么标签 / 你判断 ✅❌」对照表 | Erika 判 ❌ → 返修 |
| 3 | 线上（部署后） | 测试账号真实上传，确认线上结果与本地一致 | 不一致 → 回滚 |

**闸门 3 不可省。** 它是防"说做好了其实没生效"的唯一有效手段——只有它跑的是真的线上链路（含缓存、开关、部署配置）。缓存层那次出问题、类目范围门禁做完却默认关闭、三个软模块的 AI 开关默认关且超时 0.25 秒，都是缺这一步造成的。

## 9. 停止规则（出现即停手，先修再继续）

- 标签无原文依据仍进 TOP10 → 停下修门禁。
- 旧产品/竞品/无证据内容被算成当前产品亮点或问题 → 停下补边界。
- 卖家可行动的发货、配件、尺码表、详情页问题被藏到 candidate / audit → 停下补 TOP10 口径。
- resolver 未收到当前 category/sub_category 时仍展示正式标签 → 改 fail closed。
- registry 出现无 `scope_reason`、无正负例、无人工审核记录的 `["*"]` → 停下补证据或收窄 scope。
- active results / export / insight / 行动中心绕过统一 resolver / scope gate → 停下改入口。
- 新增第 3 类硬编码类目关键词 → 停手，改用第 1 类通用守卫或第 2 类能力声明。
- Erika 无法用样例表理解系统在做什么 → 先改输出说明，不继续写功能。

## 10. 触发式维护规则（避免一人公司变重运营）

- `other` 占比 > 15% → 该品类 taxonomy 覆盖不足。
- 某 candidate 标签出现 ≥ 10 次 → 进待处理清单。
- 同一标签被反馈错了 ≥ 3 次 → 进待处理清单。
- 某品类出现付费用户或占付费用户 > 20% → 补 mini Golden Set。
- 每次维护只处理 Top 3 候选：保留、合并、改名、禁用或补 `boundary_note`。
- 维护只由告警和付费品类触发，不做日常巡检。
