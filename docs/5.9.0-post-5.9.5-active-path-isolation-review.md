# 5.9.0 Post-5.9.5 Active Path Isolation Review

日期：2026-08-05

范围：只做 5.9.5 后的小型隔离复核与 waders 专项规则去留收口建议；不接入 active upload、worker、results、export 或 frontend；不改变 waders 运行逻辑。

## 结论

5.9.5 后，新 `review_fragment_*` 链路仍保持隔离，没有被 active upload、worker、results、export 或 frontend 默认加载。

旧 frontstage / shadow 路线仍不是完全清爽：

- Active analysis / export / `review_analyzer.exporter` import 不会默认加载 `customer_label_v2_shadow.py`，也不会默认执行 v2 runtime shadow。
- Active analysis / export / `review_analyzer.exporter` import 会加载 `review_signal_frontstage.py`；该 wrapper 顶层继续 import `review_signal_shadow.py` 的常量和 safety helper。因此默认不改用户结果，但仍有旧 shadow 文件的 active import 负担。
- `workers.jobs` import 不会默认加载 `customer_label_v2_shadow.py` 或 `review_signal_shadow.py`，但会加载 `specific_issue.py`。
- `review_analyzer.exporter` 仍依赖旧 frontstage wrapper 做 flag resolution 和可选 read model attach；默认 flag off 时不附加旧 read model，实际导出仍读 v1 `customer_label_occurrences` / `specific_issue.py` 聚合。
- waders 专项规则仍在主线默认生效：worker 写入时会调用 `specific_issue.enrich_aspects_json()`，结果页 / insight / export 读路径也会继续通过 `specific_issue` occurrence iterator 和 TOP10 builder 消费这些 occurrence。

因此，本轮审计完成，但 5.9.0 仍不应标记为完全完成；waders 专项规则去留仍待 Erika 决策。

## Feature Flag 默认状态

Active 代码使用 `*_flag_from_env()`，在 env 未设置时默认如下。

| 开关 | 默认值 | 默认行为 |
|---|---:|---|
| `CUSTOMER_LABEL_V2_FRONTSTAGE_ENABLED` | `False` | 不附加 `customer_label_v2_frontstage_read_model`。 |
| `CUSTOMER_LABEL_V2_FRONTSTAGE_ALLOW_RUNTIME_SHADOW` | `False` | 不现场执行 `run_customer_label_v2_shadow()`。 |
| `CUSTOMER_LABEL_V2_FRONTSTAGE_SHADOW_FIXTURE_GATE_PASSED` | `False` | 即使显式 enabled，也会先被 fixture gate 阻断。 |
| `CUSTOMER_LABEL_V2_FRONTSTAGE_ROLLBACK` | `False` | 无全局 rollback。 |
| `CUSTOMER_LABEL_V2_FRONTSTAGE_KILL_SWITCH` | `False` | 无全局 kill switch。 |
| `CUSTOMER_LABEL_V2_FRONTSTAGE_SESSION_IDS` / scope lists | `()` | 无 session/category/sub_category 灰度范围。 |
| `REVIEW_SIGNAL_FRONTSTAGE_ENABLED` | `False` | 不附加 `review_signal_frontstage_read_model`。 |
| `REVIEW_SIGNAL_FRONTSTAGE_RUNTIME_SHADOW_GENERATION_ALLOWED` | `False` | runtime shadow generation 不支持；若设 true 会 config invalid / fail closed。 |
| `REVIEW_SIGNAL_FRONTSTAGE_ROLLBACK` | `False` | 无全局 rollback。 |
| `REVIEW_SIGNAL_FRONTSTAGE_KILL_SWITCH` | `False` | 无全局 kill switch。 |
| `REVIEW_SIGNAL_FRONTSTAGE_SESSION_IDS` / scope lists | `()` | 无 session/category/sub_category 灰度范围。 |

补充：`CustomerLabelV2FrontstageFlag` dataclass 的字段默认值里 `allow_runtime_shadow=True`，但 active runtime 通过 `customer_label_v2_frontstage_flag_from_env()` 构造 flag；env 解析默认将 `allow_runtime_shadow` 设为 `False`。

## Export Read Path

`review_analyzer.exporter` 仍有旧 frontstage wrapper 依赖：

- import 层依赖：`customer_label_v2_frontstage_flag_from_env()`、`review_signal_frontstage_flag_from_env()`。
- read decoration：`_decorate_comments_for_export()` 调用 `decorate_comment_customer_labels()`。
- TOP10 导出：`_build_specific_issue_top10_data()` / `_build_customer_highlight_top10_data()` 调用 `build_specific_issue_rows()` / `build_customer_highlight_rows()`。
- 原始评论导出：`_join_specific_issue_field()` / `_join_customer_highlight_field()` 调用 occurrence iterator。

默认 flag off 时，旧 frontstage wrapper 不附加 v2 / review-signal read model，导出默认仍消费 `specific_issue.py` 投影出的 v1 occurrence。由于 `specific_issue.py` 读路径会继续补 waders content rule，导出仍会默认消费 waders 专项 occurrence。

## Waders 专项规则链路

### 默认写入影响

`workers/jobs.py` 对每条正常分析结果调用：

```text
result["aspects_json"] = enrich_aspects_json(...)
```

`enrich_aspects_json()` 会：

- 从 LLM aspects 归一化 issue / highlight occurrence。
- 若没有 `water_leaks_through`，尝试用 `_water_leak_occurrence_from_content()` 从原文补漏水 occurrence。
- 默认调用 `_append_waders_content_rule_occurrences(... label_type="issue")`。
- 默认调用 `_append_waders_content_rule_occurrences(... label_type="highlight")`。
- 写入 `customer_label_occurrences`、schema version 和 ruleset version。

因此，waders 规则仍会默认写入 active 分析结果。

### 默认读取影响

即使历史数据未在 worker 写入 waders occurrence，读路径仍会补规则：

- `iter_specific_issue_occurrences()` 在 occurrence schema 命中时会调用 `_append_content_rule_issue_occurrences()`。
- `_append_content_rule_issue_occurrences()` 会进一步调用 `_append_waders_content_rule_occurrences(... label_type="issue")`。
- `iter_customer_highlight_occurrences()` 在 occurrence schema 或 customer label payload 命中时会调用 `_append_waders_content_rule_occurrences(... label_type="highlight")`。
- `customer_issue_tags_for_comment()`、`customer_highlight_tags_for_comment()`、`build_specific_issue_rows()`、`build_customer_highlight_rows()` 都消费这些 iterator。

### 前台 / insight / export 消费

- 结果页 API：`analysis.py` 先 decorate comments，再调用 `build_results_insights()`。
- Insight：`review_analyzer/insight_engine.py` 调用 `build_specific_issue_rows()` / `build_customer_highlight_rows()` 生成用户体验、购买动机、未满足需求和建议里的标签输入。
- Module export：`backend_api/app/routes/export.py` 调用 `build_specific_issue_rows()` / `build_customer_highlight_rows()`。
- Full export：`review_analyzer/exporter.py` 调用 occurrence iterator 和 TOP10 builder。
- Frontend：`frontend/src/lib/customer-labels.ts` 默认读取 `customer_label_occurrences`，并继续执行 waders context guard，例如水漏、配件漏水、hanger missing、traction、breaks easily 等过滤。

## Waders 三选一建议

三种路径：

| 选项 | 判断 |
|---|---|
| A. 短期保留为现有前台安全补丁 | 推荐。本规则已经在 active 结果页 / 导出中承担 waders 防错和召回补丁，马上移除会改变现有用户可见结果。 |
| B. 抽成 category-specific compatibility module | 中期建议。在 5.9.6 前可先不改逻辑，后续把 waders 规则从 `specific_issue.py` 抽到显式命名模块，例如 `category_specific/waders_compat.py`，降低主文件认知成本。 |
| C. 等新链路替代后分批删除 | 最终方向，但不建议现在直接选择为立即动作。需要新 `review_fragment_*` 接入 active 且通过 5.9.7 小样本验收后，再按规则组分批删除。 |

本轮建议：选择 A 作为短期产品策略，同时把 B 作为 5.9.6 前后的工程收口方向；C 作为新链路完成后的删除策略。由于 Erika 尚未明确批准，5.9.0 仍保持“待决策”。
