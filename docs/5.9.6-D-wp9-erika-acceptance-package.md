## 材料 1：Scope Diff — 从 `["*"]` 到规则驱动的 scope

**这份材料回答：** 5.9.6-A 时期所有标签都是全局 89 品类生效。5.9.6-D 收窄后，每个标签现在覆盖多少品类？收窄的依据是什么？Erika 之前质疑过的 waterproof、seam_integrity、accessory_storage 三个标签为什么只适用特定品类？

### 1.1 收窄总览

| label_key | 旧 scope（5.9.6-A） | 新 scope（5.9.6-D） | 收窄幅度 | scope_policy | 一句话理由 |
|-----------|-------------------|-------------------|---------|-------------|-----------|
| `late_shipping` | 89（全部） | 89（全部） | 不变 | `transaction_universal` | 发货速度是所有线上实物商品的通用交易体验 |
| `shipping_damage` | 89（全部） | 89（全部） | 不变 | `transaction_universal` | 运输损坏是所有线上实物商品的通用交易体验 |
| `customer_service_unresponsive` | 89（全部） | 89（全部） | 不变 | `transaction_universal` | 客服响应是所有线上实物商品的通用交易体验 |
| `customer_service_helpful` | 89（全部） | 89（全部） | 不变 | `transaction_universal` | 客服质量是所有线上实物商品的通用交易体验 |
| `water_leaks_through` | 89（全部） | **5** | 89→5 | `capability_derived` | 产品进水只对防水/接缝类产品有意义 |
| `keeps_water_out` | 89（全部） | **5** | 89→5 | `capability_derived` | 保持干燥只对防水类产品有意义 |
| `accessory_leak` | 89（全部） | **1** | 89→1 | `capability_derived` | 配件漏水只对有配件收纳的产品有意义 |
| `missing_accessory` | 89（全部） | **1** | 89→1 | `capability_derived` | 缺少配件只对有配件收纳的产品有意义 |
| `confusing_size_chart` | 89（全部） | **16** | 89→16 | `capability_derived` | 尺码表只对按离散码数售卖的产品有意义 |

**关键结论**：
- 4 个交易层标签保持全局生效（89 品类），因为它们描述的是"线上购物"这个共同场景，与卖什么产品无关
- 5 个产品层标签收窄到特定品类，范围由 taxonomy 中该品类是否声明了相关能力维度决定
- 没有一个标签使用 `explicit`（手写列表），全部由规则计算

### 1.2 重点标签：为什么 water_leaks_through、accessory_leak、missing_accessory 只适用特定类目

这三个标签是 Erika 之前明确质疑过的——"漏水"、"配件漏水"、"缺少配件"看起来像是通用问题，为什么不能在所有品类生效？

#### water_leaks_through（容易进水）— 仅 5 个品类

**收窄逻辑**：这个标签描述的是"产品本身进水"——水从外部进入产品内部。它需要产品具备防水能力维度（waterproof）或接缝密封能力（seam_integrity）。

- 保温杯漏水是**密封性问题**（杯盖不严），不是产品进水——保温杯 taxonomy 没有 waterproof 或 seam_integrity
- 化妆品渗漏是**包装问题**，不是产品进水
- 狗粮受潮是**包装密封**，不是产品进水

**生效的 5 个品类**：

| 品类 | 匹配的能力维度 |
|------|-------------|
| waders（涉水裤） | waterproof + seam_integrity |
| 冲锋衣 | waterproof |
| 帐篷 | waterproof |
| 户外背包 | waterproof |
| 登山鞋 | waterproof |

**不生效的例子（会触发 out_of_scope 拒绝）**：
- 保温杯 → 拒绝（没有防水/接缝维度，杯体漏水是密封性问题）
- Baby Sun Hat → 拒绝（婴儿遮阳帽不需要防水）【已有 CI 锁定：`test_water_leaks_through_rejected_on_baby_sun_hat`】
- Cosequin for Dogs → 拒绝（宠物保健品跟防水无关）【已有 CI 锁定：`test_water_leaks_through_rejected_on_cosequin`】

#### accessory_leak（配件漏水）— 仅 1 个品类（waders）

**收窄逻辑**：配件漏水是"产品附带的收纳组件（口袋、手机袋等）进水"。这需要产品在 taxonomy 中声明了 `accessory_storage`（配件收纳）维度。

当前 89 个品类中，只有 **waders（涉水裤）** 的 taxonomy 声明了 `accessory_storage`。这不是说其他产品没有配件，而是**当前 taxonomy 中没有其他品类的评论谈论过"配件"这个维度**。

> **注意**：如果后续 taxonomy 新增了其他有 accessory_storage 的品类（比如钓鱼背心、战术背包），这两个标签的 scope 会**自动扩展**，不需要改 registry。这是 `capability_derived` 的核心优势。

#### missing_accessory（缺少配件）— 仅 1 个品类（waders）

**收窄逻辑**：同上，依赖 `accessory_storage` 维度。保温杯缺少清洁刷、数据线缺少说明书——这些是通用缺件，不是"配件收纳"维度下的问题。

### 1.3 confusing_size_chart 的收窄链路：从 63 → 16

这是 5.9.6-D 中最关键的收窄决策之一。

**5.9.6-D 之前**：`confusing_size_chart` 的 `aspect_keys` 是 `[size_fit]`。`size_fit`（尺码与版型）是通用维度，89 个品类中有 63 个声明了它——从婴儿袜子到宠物保健品都有 `size_fit`。

**问题**：`size_fit` 太宽了。"药片太大狗吞不下"（Cosequin for Dogs）是尺寸适配问题，但跟"尺码表"没关系——Cosequin 不按 S/M/L 卖，没有尺码表。把药片大小问题标成 `confusing_size_chart` 是标签错配。

**5.9.6-D WP5 修正**：将 `aspect_keys` 从 `[size_fit]` 改为 `[size_chart]`。`size_chart` 是新增的 aspect，只声明在**按离散码数（S/M/L 或数字码）售卖、且卖家提供尺码表**的品类上。taxonomy 中只有 16 个品类声明了 `size_chart`。

| 维度 | aspect | 覆盖品类数 | 典型品类 |
|------|--------|----------|---------|
| 修改前 | `size_fit` | 63 | 衣服、鞋、宠物用品、婴儿用品... |
| 修改后 | `size_chart` | 16 | 涉水裤、冲锋衣、连衣裙、内衣、婴儿连体衣... |

**被排除的 47 个品类举例**：Cosequin for Dogs、Probiotics for Dogs、Dog Treats、Baby Bibs、Odor Eliminator——它们有 `size_fit`（尺寸/剂量适配）但没有 `size_chart`（尺码表）。

### 1.4 为什么 4 个交易层标签保持全局生效

`late_shipping`、`shipping_damage`、`customer_service_unresponsive`、`customer_service_helpful` 这 4 个标签都是 `transaction_universal`。

它们的共同特征：描述的是**交易层体验**——物流、包装、客服——而不是产品本身的物理能力。不论是卖涉水裤还是卖保温杯还是卖狗粮，买家都关心发货快不快、到货有没有损坏、客服回不回消息。

**护栏**：每个 `transaction_universal` 标签必须声明 `required_transaction_dimension`，且只能从 `data/taxonomy/shared/transaction_aspects.yaml` 的封闭枚举（3 个值）中选：
- `logistics_issue`（物流问题）
- `customer_service`（客服）
- `packaging`（包装）

这个封闭枚举防止"交易通用"变成新的 `["*"]`——没有这条护栏，任何标签都可以宣称"跟产品类型无关"然后全局生效。

### 2.3 review_status 说明

当前 9 个标签的 `review_status` **全部为 `pending`**。这是决策 p 的预期状态：

- `review_status` 是 5.9.6-D 新增的治理字段，独立于 `status`（标签本身的 approved/candidate/blocked）
- `status=approved` 意味着标签的定义和迁移已完成
- `review_status=pending` 意味着 scope_policy、negative_examples 等治理字段等待 Erika 人工审核
- 在 `approved_only=True`（默认）下，resolver 的 Gate 2 检查的是 `label.status`（不是 `review_status`），所以当前 9 个标签都能正常通过 resolver
- 等 Erika 在 5.9.7 确认 scope 和负例无误后，可以在审核页批量将 review_status 改为 `approved`

### 3.3 Resolver 的 4 道 Gate（拒绝顺序）

Resolver 对每个标签按以下顺序检查，任一 gate 失败即返回拒绝：

| Gate | 检查项 | 举例 |
|------|--------|------|
| Gate 1 | category_key / sub_category_key 不能为空 | 空字符串 → `unknown_key`（fail-closed） |
| Gate 2 | label.status 必须是 approved（当 `approved_only=True`） | candidate 标签 → `not_approved` |
| Gate 3 | sub_category 必须在 effective scope 内 | 保温杯 + water_leaks_through → `out_of_scope` |
| Gate 4 | sub_category 不能在 blocked_contexts 中 | waders 被手动 blocked → `blocked_context` |

**Gate 排序验证**（测试 `test_resolver_gate_ordering_*`）：
- Gate 2（not_approved）优先于 Gate 3（out_of_scope）：当标签同时不 approved 且在范围外时，返回 `not_approved`
- Gate 3（out_of_scope）优先于 Gate 4（blocked_context）：当品类同时在范围外且被 blocked 时，返回 `out_of_scope`

### 3.4 为什么 out_of_scope = "不会进 TOP10"

当 resolver 返回 `is_resolved=False, reject_reason='out_of_scope'` 时：

1. **前台展示（WP6 shadow 模式）**：shadow pass 记录这条拒绝事件到日志，但不影响用户看到的标签列表（flag=off 时旧路径决定展示；flag=shadow 时旧路径决定展示但记录差异）
2. **enforce 模式（5.9.7+）**：被拒标签直接从正式标签列表中移除
3. **TOP10 统计**：只有 `is_resolved=True` 的标签才计入正式标签统计
4. **导出**：导出的正式标签列表中不包含被拒标签

**一句话**：被 Gate 3 拒绝的标签 = 这个品类不该有这个标签 = 不会出现在用户的 TOP10 里。

### 3.5 Fail-Closed 验证

## 材料 4：Registry Proposal 样例

**这份材料回答：** 如果以后发现错标（标签在不该出现的品类出现了，或该出现的没出现），怎么通过 proposal 回流到 registry？从"发现问题"到"改完 YAML + 生成测试"的完整链路是什么样的？

### 4.1 链路概览

```
发现问题（shadow diff / 人工审查）
  → 调用生成助手创建 proposal（落 DB，status=pending）
  → 审核页 Registry Review tab（`/settings/golden-set`，WP8 已并入）查看候选队列
  → Erika 审批：approve / reject
  → 如果是 merge：写回 YAML → 跑 validate_label_scope.py → 失败则回滚 → 生成负例测试
```

### 4.2 4 种 Proposal 类型

每种类型对应一种"发现的问题"，各有一个生成助手函数：

| action_type | 解决的问题 | 生成函数 | 写回 YAML 哪个字段 | 是否生成测试 |
|------------|-----------|---------|-------------------|------------|
| `scope_adjust` | 某个标签在某品类频繁被误拒（应该生效但没生效） | `generate_scope_adjust_proposal()` | `scope_policy` / `aspect_keys` | 否（scope 变化需要人工确认） |
| `alias_merge` | 两个 label key 语义重复 | `generate_alias_merge_proposal()` | `aliases`（合并进 target 的别名列表） | 否（合并是语义操作） |
| `blocked_rule` | 某标签在特定上下文误命中 | `generate_blocked_rule_proposal()` | `blocked_contexts` | 否（block 是状态级减法） |
| `negative_example` | 某条评论被误标 | `generate_negative_example_proposal()` | `negative_examples` | **是**（自动生成负例回归测试） |
