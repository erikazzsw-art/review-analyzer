## 人工重点看哪里

1. 正式产品问题是否都有 `issue_key`。
2. 正式产品亮点是否都有 `highlight_key`。
3. `aspect_key` 是否都像证据维度，而不是卖家展示标签。
4. `late_shipping` 和 `shipping_damage` 是否都应该归入 `aspect_key=logistics_issue` 这个物流大类。
5. `candidate_label_key` 是否只用于候选行，不进入正式 TOP10。
6. 行动中心不需要标准动作 key 是否可接受。

## 物流字段区分

| 层级 | key | 含义 | 示例证据 |
|---|---|---|---|
| aspect_key | `logistics_issue` | 物流 / 履约证据大类，用于承接发货、送达、到货状态等物流相关证据。 | `Shipping was late`、`box arrived crushed` |
| issue_key | `late_shipping` | 物流时效问题，表示发货晚、送达晚、配送延迟。 | `Shipping was late` |
| issue_key | `shipping_damage` | 物流损坏 / 到货状态问题，表示到货破损、错发、已使用、脏污等。 | `box arrived crushed` |

审批口径：`shipping_damage` 不再作为正式 artifact 的 `aspect_key` 使用；它只作为具体正式问题 `issue_key`。`late_shipping` 和 `shipping_damage` 都挂在 `aspect_key=logistics_issue` 下。

## 字段删除验证

| 字段 | 当前状态 |
|---|---|
| `action_label_key` | 正式 artifact 不输出；validator 只保留 `action_label_key_forbidden` 负向检查。 |
| `normalized_label` | 正式 artifact 不输出；validator 只保留 `normalized_label_forbidden` 负向检查。 |
| `recommended_action_key` | active schema / action route / action store / 前端 action center 均不依赖；测试只验证它不会进入 payload 或响应。 |

## 行动中心输入口径

行动中心继续接收和展示：

| 字段 / 数据 | 用途 |
|---|---|
| `canonical_issue_key` / `issue_key` | 识别要跟进的正式问题。 |
| `aspect_key` | 展示问题所属证据维度。 |
| `specific_issue` / `tag_name` | 展示给用户看的问题文本。 |
| `source_reviews_json` | 代表性评论证据。 |
| `current_pct` | 当前占比。 |
| `suggested_action` / `ai_suggestions_json` | AI 生成行动建议文本。 |

不需要 `recommended_action_key`。如果未来要做标准动作模板，应另做行动规则层，不放进当前标签注册中心。
